# 评测指标迁移说明：文件级语义覆盖

## 摘要

AACR-Bench 的默认评测指标已从**逐条一对一匹配**（语义 / 行号两套
Precision / Recall / F1）切换为**文件级语义覆盖**
（`file_semantic_match_rate` / `file_semantic_recall_rate` /
`balanced_score`）。

切换动机来自实证观察：模型——尤其是较强的 LLM 评审器——经常会在**一条
评审意见中指出多个不同的问题**。旧的一对一匹配对这样的评论只能计分一次，
导致命中数和召回率被系统性低估，指标读数虚低。

旧指标体系仍可通过 `--use-deprecated-score` 启用，并将在后续版本中移除。

## 背景：旧匹配流程

旧评测器（`evaluation/judge.py` 中的 `evaluate_comments`）遍历每条参考评论
（ground truth），在生成评论中按四个阶段依次过滤：

```
path → side → line(k) → semantic
```

- **path / side**：文件路径与 diff 侧别的硬相等。
- **line(k)**：硬门槛——生成评论的行号区间必须与参考评论重叠或距离 ≤ k
  （双方都带行号信息时生效）。
- **semantic**：逐对调用裁判模型判断两条评论是否表达相同的问题。

关键在于匹配是**全局消耗式的一对一**：每条生成评论在语义匹配中最多只能
被一条参考评论消耗一次（`matched_gen_ids_by_semantic`）。

## 为什么旧指标虚低

### 1. 一条评论多个问题，但只能计一次分

真实的评审输出并不遵循标注数据集"一条评论一个问题"的约定。一条生成评论
例如：

> "这个方法吞掉了异常并返回 null；调用方会 NPE，而且失败的事务没有回滚。"

可能真实地覆盖了分别标注的两到三条参考评论。在一对一匹配下，第一条参考
评论消耗掉这条生成评论后，它覆盖的其余参考评论全部被记为**未命中**——
直接压低召回率。

### 2. 逐对裁判对多问题评论不利

旧的语义阶段是一对一比较。当生成评论打包了多个问题时，裁判看到的是一段
长文本，其中只有一部分与参考评论对应，即使问题确实被覆盖，也容易得到
"不相似"的边缘判决。

### 3. line(k) 门槛在裁判之前就把正确评论筛掉了

双方都带行号信息时，指向同一问题但行号略有偏移的生成评论根本进入不了
语义阶段。对 LLM 评审器而言，行号是一个噪声很大的硬过滤器——模型经常把
正确的问题锚定在相邻行上。

### 示例

假设某文件有两条参考评论（GT-1、GT-2），模型输出一条同时覆盖两者的评论：

| | 旧（一对一） | 新（文件级） |
|---|---|---|
| GT-1 | 命中（评论被消耗） | 被覆盖 |
| GT-2 | **未命中**（评论已被消耗） | 被覆盖 |
| 召回率 | 1/2 = 0.5 | 2/2 = 1.0 |
| 准确率 | 1/1 = 1.0 | 1/1 = 1.0 |

模型完全做对了，旧召回率却仍然报 0.5。

## 新指标体系：文件级语义覆盖

默认评测器（`evaluation/judge.py` 中的 `evaluate_file_level_semantics`）
工作流程如下：

1. **按文件分组。** 参考评论与生成评论按归一化文件路径分组；side 与行号
   不再是硬过滤器，行号区间仅作为上下文提供给裁判。
2. **每条生成评论一次裁判调用。** 每条生成评论与同文件内**全部**参考评论
   组成的编号列表一次性比对。裁判被明确要求忽略措辞、语气、格式与具体
   行号，返回所有表达相同问题的参考评论编号——即**一对多覆盖**是一等
   公民结果。
3. **准确率贪心去重。** 按生成顺序处理，一条生成评论只有在命中至少一条
   此前未被覆盖的参考评论时才计入准确率分子（`hit_new_gt`）。仅仅重复
   覆盖已被覆盖参考的评论标记为重复命中，不计入准确率分子，避免重复
   命中虚高准确率。

### 指标定义

| 指标 | 定义 |
|---|---|
| `file_semantic_match_rate`（准确率） | 命中 ≥1 条此前未覆盖参考评论的生成评论数 / 生成评论总数 |
| `file_semantic_recall_rate`（召回率） | 被 ≥1 条生成评论覆盖（去重）的参考评论数 / 参考评论总数 |
| `balanced_score` | 准确率与召回率的调和平均 |

### 审计信息

每条参与评测的生成评论都会记录在指标 JSON 的
`eval_res[].generated_comments[]` 中：

- `matched_gt_indices`：该评论覆盖的参考评论下标（指向同条目的
  `comments` 数组）；
- `judge_reason`：裁判对每条参考评论的判定理由；
- `hit_new_gt`：是否命中了至少一条此前未被覆盖的参考评论（false 表示
  重复命中，不计入准确率）。

落在无参考评论文件下的生成评论也会记录（`matched_gt_indices` 为空），
但不调用裁判模型。

## 迁移注意事项

- **模式标记**：结果 JSON 带有 `ex_info.score_mode`
  （`"file_semantic"` | `"deprecated"`），下游工具可据此区分数字由哪套
  体系产出。
- **`--line-k` 仅在 deprecated 模式下生效**；文件级体系把行号区间作为
  上下文交给裁判，而不再用它做过滤。
- **两种模式的数值不可比。** 不要在同一张表或图中混用新旧分数；历史
  基线请在新体系下重新评测。
- 当前指标体系的完整字段参考见 [metrics.md](metrics.md)。
- 用法细节见 [../evaluation/README.zh-CN.md](../evaluation/README.zh-CN.md)
  的「执行评测」一节。
